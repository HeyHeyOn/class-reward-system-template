# Task21 synthetic durable terminal intent / seal

> **과거 실험 기록:** Task1–24 계획에 속한 당시의 합성 검증·복구 실험이다. 현행 A–F의 실행 순서나 현재 운영 완료율을 나타내지 않는다. 현재 상태는 [README](../README.md)를 따른다.

NONPRODUCTION ONLY. This is an opt-in bounded extension to the existing product chain, not Task21 completion, a CDC service, an operational writer fence or a promotion. No Next or HTTP API is changed.

## Protocol and trust roots

1. Retain the original admitted native archive and full `MaterializedArchiveExpectation` through the existing private cold coordinator. Retain the random chain ID and SHA256(canonical entire expectation) separately from segment transport.
2. Create a distinct, empty, parent-owned isolated synthetic PostgreSQL coordinator. `initializeTerminalCoordinator` commits its immutable private lease: exact database UUID, owner UUID, PostgreSQL system identifier, and original complete public-state digest. The caller independently retains that exact owned resource handle and returned pin. Container ID, label, image/isolation and native PG identity are checked on every call; neither endpoint nor resource discovery is derived from an uploaded artifact.
3. Before the first controlled product segment, `registerProductChainIntent` commits an immutable private source intent, bound to the full admitted parent, chain ID and source PG system. Its plan is a bounded ordered list of event counts (1–32 segments, 1–100 events each). An identical cold-process retry is allowed; a conflicting plan, late opt-in or another parent/chain is not.
4. Existing capture atomically commits each product transaction and its SQL outbox entry. With an intent present, each segment must match the planned ordinal and event count; an extra segment is refused before DML. Finalization is not inferred from the latest received segment.
5. `retainProductChainTerminal` reads the full authenticated source outbox, reconciles exact current public rows/sequences/guards, requires every planned segment, then commits the immutable source seal. The seal contains the intent plus EVERY segment's ordinal, cumulative checkpoint and full artifact digest. In a separate transaction it copies that seal into the independently authenticated coordinator's private SQL state. It takes a source handle, NOT caller-provided seal bytes. Repeating these calls after application-process exit reads the same committed SQL. Do not delete the source until coordinator commit AND independent SQL readback have succeeded.
6. After controlled source deletion and a fresh native restore, `installProductChainTerminal` obtains the seal ONLY by directly authenticating and reading that separate coordinator. It refuses absent/conflicting/foreign state and binds the installed immutable record to this destination's database, owner and PG system identity. First installation is only allowed before any segment replay. Installation cannot mutate public rows. No raw-seal import API exists.
7. `replaySealedProductSegment` refuses without an installed terminal, validates the incoming digest against its planned entry, and uses the existing exact SQL journal/public-state/DML transaction. All existing chain replay calls also enforce the terminal when installed. Old unsealed chain and single-segment APIs remain legacy bounded behavior, NOT evidence of sealed-chain completion.
8. `verifyProductChainTerminal` is the explicit read-only completion gate. It requires the whole planned SQL journal, exact authenticated terminal and full public row/sequence/guard reconciliation. A valid prefix never passes. An installed seal also prevents the old caller-endpoint checkpoint verifier from blessing a shorter prefix. Replaying an exact current tip is intentionally `ALREADY_APPLIED`, including a terminal tip, not a conflicting duplicate. Historical/reordered/extra/conflicting segments still refuse.

## Persistence, isolation and failure semantics

Source intent/seal, coordinator lease/seal and installed destination seal are singletons in owner-only private schemas; no public schema migration or runtime grant is added. Update/delete/truncate are rejected by triggers. SHA256 plus canonical encoding catches corruption relative to the trusted private SQL state; it is NOT an upload signature. The threat boundary assumes trusted launcher/same-UID control-plane files and non-malicious synthetic PG superusers. Runtime SQL cannot read or rewrite the records. Public RLS/guards stay enabled and unchanged.

Private state and public writes share their respective native PG transactions. Source-seal commit and coordinator commit are deliberately NOT a distributed atomic transaction. If publication fails after source seal commits, the source remains sealed and an identical retry can finish publication; a destination with no independently retained seal fails closed. The owning launcher remains responsible for retaining resources and preventing premature deletion. No test-only kill switch is added to production code.

The separate coordinator is an actually exercised independent owned-PG path across cold APPLICATION-process restarts, not the segment transport, a caller's guessed endpoint or an audit-only convention. However its disposable cluster is tmpfs-backed and the parent launcher remains live: this proves application-restart persistence only. PG/container/host restart, power-loss/fsync durability, independent cross-host signed/secrets-backed delivery, lost-launcher ownership recovery, and real COMMIT-response-loss fault injection remain UNSOLVED/UNPROVEN. The retained coordinator handle/pin still needs trustworthy lifecycle/transport outside this synthetic launcher; neither uploading its JSON nor finding a container by name is sufficient. STOP rather than adopt resources or real credentials to bridge that boundary.

Completeness is only relative to the declared bounded product chain. Event-count intent does not know business writes the trusted producer omitted before capture. Non-product mutations, concurrent outside writers, WAL/CDC completeness, a global source commit order and arbitrary future suffixes remain unsupported. An unavailable/missing coordinator is not repaired from transport. The source cannot safely be deleted before its seal is independently retained. This protocol does not confer actual authority.

## Executable evidence scope

The terminal positive/negative PG suite initializes/retries the coordinator in separate child processes; registers/retries source intent; refuses early seal attempts after valid prefixes; captures three product segments with cumulative checkpoints 2, 4, 6 using existing cold chain writers; retains/retries seal; independently reads source/coordinator SQL; deletes the source before the restore process starts; restores a fresh disposable destination; installs/retries through the separate coordinator; replays/retries in separate child processes and explicitly verifies terminal completion in another cold process.

Raw SQL public witnesses are compared with each source checkpoint, with non-default sequence `last_value/is_called` and exact guard definitions. Only the four pre-existing provenance tables have source/destination-specific values, separately authenticated by the restore/chain contract. Negative calls compare complete public and private before/after witnesses. Coverage includes missing seal, valid incomplete prefixes (also through the legacy endpoint API), forged coordinator identities/raw seal shape, wrong chain/tenant/parent, terminal metadata smuggling, tampered segments, extra successor, and immutable conflicting-seal writes. Existing product-chain positive/negative and single-segment tests remain required regressions.
