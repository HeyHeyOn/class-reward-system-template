# FREEZING start ceremony checkpoint

## Status and stop line

This slice implements explicit pending intent, purpose-separated authenticated callback continuation, acknowledged one-dispatch reservation, authentic bridge intake and the atomic **READY → FREEZING** consumer. Production start route exports, production start factory configuration and the confirmation UI remain integration gates. The [durable companion producer](migration-bridge-producer.md) now supplies the fixed authenticated route, deployment-local credential factory and replay SQL adapter, but no live registration or invocation is enabled by this code change. The ordinary production consent factory remains consent-only; the new consumer is an internal server composition seam, not an enabled production writer-disable call.

A local synthetic transport response is not a verified bridge acquisition. `BRIDGE_RESPONDED_START_NOT_COMMITTED` is deliberately not `FREEZING`, `STARTED`, `FINAL_FROZEN`, or writer-exclusion evidence. Existing job/tenant/acquisition/global claim state is not changed by dispatch. Maintained writer exclusion remains `NOT_PROVEN`.

## Explicit confirmation, not receipt promotion

- A server-owned `StartFreezingRegistration` binds tenant, source, exact raw spreadsheet ID, deployment ID, registration version and registration digest. The registration digest must match the actual registered client's configuration. No browser endpoint, key, reader, writer control or provider credential is accepted.
- In configured start mode, consent challenge issuance and `migration_start_intents` insertion/readback are in the same transaction. The immutable intent binds the exact consent challenge digest/session, semantic fingerprint, source acquisition digest, exact PREFLIGHT identity/digest and displayed action `DISABLE_LOCAL_WRITER_AND_START_FREEZING`. Automatic enable is explicitly false.
- Ceremony ID equals the newly issued consent challenge ID. The TTL is exactly 300 seconds from that challenge's DB issuance timestamp. Confirmation, OAuth and bridge issuance never renew it. Standalone approval and bridge lifetimes remain 60 seconds.
- The actual same-origin POST requires the issued synchronizer and exact full `display`. Consent confirmation and start confirmation share one acknowledged transaction. Start confirmation binds the exact OAuth state digest and immutable intent digest.
- The encrypted routing cookie retains the existing host-only, `/api/`, HttpOnly/Secure/SameSite=Lax design, with a separate start-purpose key derivation and AAD. Start hints also bind intent digest. The canonical directory, exact challenge/intent and current session rebind the hint; a consent-only cookie cannot be promoted, even if a pending row exists.
- The existing consent acquisition purpose and narrow `CONSENT_AND_SHEET_CAPTURE_ONLY` receipt remain unchanged. Only a fresh configured start callback, after acknowledged reservation, real provider verification/capture, revoke+clear and capture COMMIT ACK, obtains additional private start metadata. The metadata has no public mint/recovery setter. IDs, JSON, archived captures and ordinary live consent fail the registry check.
- `continueStart` is awaited before responding, never scheduled as a detached task. The ordinary consent callback still returns only `CAPTURED` and its narrow scope.

## Dispatch boundary

`StartFreezingBridgeAdapter.prepare(intent)` must issue a fresh real bridge challenge and prepare/sign the exact request **without contacting the producer**. It returns `challenge`, `requestDigest` and single-use `send()`; the registered client's prepared request can be composed with this seam. Its send result must be `{outcome:'RECEIVED', manifest}` or a terminal uncertain/not-sent outcome.

The orchestrator checks private start metadata before its first await, detaches request/configuration and reuses the consent intake's real READ COMMITTED tenant → job → source FOR UPDATE → current membership/session/PREFLIGHT checks. It records a DB-clock lower bound after consent ACK before bridge preparation, preventing substitution of a pre-consent challenge. The prepared challenge must match source, actor, state/version, independent fingerprints and registered deployment.

Before send, a short transaction freshly revalidates the entire consent/start binding, reads the exact durable bridge challenge, inserts the unique ceremony → bridge challenge + registration digest + request digest reservation, verifies exact readback and checks clocks again. Only an acknowledged COMMIT permits the next step. Another short current-membership/session/TTL check follows immediately before send; no transaction spans producer work.

`migration_start_dispatches` has globally unique ceremony and bridge challenge dimensions, references the start confirmation, acknowledged consent capture and bridge challenge, and is immutable under UPDATE/DELETE/TRUNCATE with forced tenant RLS. Duplicate or uncertain reservation ACK never sends. Network timeout, a registered client `UNKNOWN` result, or failed post-send revalidation remains terminal `UNKNOWN`, preserves the reservation and never retries or automatically enables the writer. A transport response remains unverified until the separate authentic intake accepts it.

## Atomic local start and archival uncertainty

`continueStartFreezing` awaits the existing dispatch, authentic `finalBridgeIntake.accept` and `startFreezing` within the same fresh callback invocation. The handler serializes `STARTED` only after the final acknowledged commit; consent-only remains `CAPTURED`. A continuation failure returns terminal 202 `UNKNOWN` with externalEffect UNKNOWN, because the writer may already be disabled and local COMMIT acknowledgement may have been lost. Dispatch-only callers retain their explicitly uncommitted 202 response.

The atomic consumer requires live start-bound consent, a live authenticated bridge acquisition and the private same-consent dispatch record **before its first await**. The bridge intake privately retains the exact challenge, canonical signed-envelope digest, purpose-framed global nonce digest, envelope lifetimes and verified writer-evidence digest. It has no archival re-mint API. A genuine unrelated bridge challenge, JSON clone or consent-only handle cannot replace this linkage.

One READ COMMITTED transaction reuses the actual current-session/membership checks and tenant → job → source FOR UPDATE lock order, then checks the exact dispatch, bridge challenge/nonce and consent capture bytes. It re-normalizes the bridge's complete Sheet+Redis pair. BLOCKED/quarantine/BANK candidates refuse start; separately captured OAuth Sheet-only semantic diagnostics do not replace complete-pair eligibility. OAuth authentication and acquisition format remain mandatory. The fresh OAuth Sheet, bridge Sheet, original acquisition and original semantic fingerprint are independently linked, never equalized or described as an atomic snapshot.

`0021_start_freezing_executions.sql` adds immutable forced-RLS consumption with globally unique ceremony, consent challenge and bridge challenge identities, parent FKs and an immutable audit reference. The existing audit store retains a bounded `AUTHENTIC_START_ACQUISITION` complete pair and normalization. Execution binding separately retains consent/capture/acquisition references, bridge challenge/envelope/nonce/Sheet/Redis/normalization/writer-evidence digests, registration and exact request digests. Exact insertion/readback and READY + expected safe version + original semantic fingerprint CAS commit together. The CAS sets FREEZING, increments version once and uses DB time for freeze_started_at/updated_at. The safe-integer overflow boundary refuses rather than rounding.

Session, membership, source, exact-one PREFLIGHT and all lifetimes are checked after waits, after execution insertion/readback and after CAS/job readback. Tenant remains IMPORTING, final_fingerprint/freeze_verified_at remain NULL and exclusion stays NOT_PROVEN. Existing snapshots, grants, targets, checkpoints, operations and global claims/tombstones are not published or changed. No FINAL_IMPORT/ACTIVE authority is minted.

Insertion suppression, wrong readback, expired authority or CAS failure rolls back only this local start transaction, **not** earlier consent/bridge tombstones or an already-disabled external writer. A local attempt is terminal even if an injected runner tries to retry its transaction callback. The production single-attempt transaction runner discards an uncertain COMMIT connection. `readStartFreezingStatus` requires the actual current identity/membership and exact tenant/job/ceremony/intent digest, and returns only an `ARCHIVAL_ONLY` fact. It never restores handles, repeats provider work or enables a writer. No public status route is introduced here.

## Verification scope

Local tests execute all production SQL migrations under the restricted PGlite runtime, real Google OAuth cryptographic verification against synthetic signed provider transport, real workbook capture/cleanup and actual normalization/import/READY generation. The atomic integration executes real normalization/import/READY, signed synthetic OAuth, the registered signed client, actual producer with production durable SQL reservations, authentic sealed intake and final local CAS. Only provider/HTTP/control-plane/Redis/Sheets and SQL transport are local fixtures; there is no mocked high-level start success. An HTTPS deny guard prevents accidental CJS/ESM SDK egress. A separate handler composition test exercises actual explicit POST/routing-cookie callback through the tenant dispatcher to STARTED. SQL/Drizzle column, constraint, check and FK parity includes the execution relation. Populated authoritative claims/tombstones/grants and every non-start table are compared before/after. Suppression, TTL, unrelated genuine handle, replay, safe-version and actual-runner post-COMMIT ACK-loss cases are covered.

These tests do not establish separate-connection PostgreSQL races or real packet loss. The new callback integration uses the server handler factory and registered producer core, not a provisioned production start factory or canonical start route exports. Producer production factory/route transport has separate existing tests, not a claim of one provisioned production end-to-end deployment. Production configuration, canonical production start route exports, a browser confirmation UI, maintained fleet/human/in-flight writer exclusion and final import/activation remain unimplemented or unproven in this slice. Existing immutable evidence and old migration SQL are not rewritten. Parent deletion across the new retained FKs is intentionally blocked; retention requires separate approval.
