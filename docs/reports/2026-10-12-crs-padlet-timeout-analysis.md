# CRS 패들렛 자동 확인 시간 초과 원인 분석

작성일: 2026-10-12 · 대상: 운영 학급 **2026 가동초 5-6** · 범위: 조사와 재현, 제품 및 운영 설정 변경 없음

현재 확인된 칭찬카드 게시판의 오류는 **`TIMEOUT`**이다. CRS 자동 확인이 여러 게시판에 짧은 시간을 나눠 쓰면서, 뒤에 확인하는 칭찬카드 게시판에 남은 시간만 주는 구조가 사용자 증상과 일치한다. 책스타그램과 칭찬카드의 과제 내용이 달라서 다른 정책을 적용하는 것은 아니다. **책스타그램은 먼저, 칭찬카드는 나중에 읽고 있다.**

수동 ‘지금 확인’은 게시판마다 8초를 주므로 자동 확인보다 훨씬 여유가 있다. 수동으로 한 번 성공해도 이 시간 배분 방식은 바뀌지 않아 다음 자동 확인에서 경고가 다시 생길 수 있다. 같은 게시판을 연결한 세 과제는 오류 상태를 공유하므로 함께 정상으로 돌아오고 함께 경고를 표시한다.

## 운영에서 확인한 사실

사용자가 지정한 소유 계정과 학급을 DB에서 대조한 뒤, 해당 학급의 연결 설정과 마지막 확인 상태만 읽었다. 아래 시각은 모두 한국 시각이다.

| 확인 항목 | 책스타그램 올리기 | 칭찬카드 쓰기 |
| --- | --- | --- |
| 연결 과제 | ①·②·③ 세 과제 | 지정 번호·자유 ①·자유 ② 세 과제 |
| 자동 조회 순서 | 첫 번째 | 두 번째 |
| API 키 | 같은 학급에 저장된 공통 키 | 같은 학급에 저장된 공통 키 |
| 특정 섹션 제한 | 없음 | 없음 |
| 마지막 확인 결과 | 성공, 오류 없음 | `TIMEOUT` |
| 마지막 확인 시각 | 10월 12일 14:59:37.131 | 10월 12일 14:59:37.669 |
| 마지막 성공 시각 | 10월 12일 14:59:37.131 | 10월 12일 14:53:58.503 |

이 상태는 15:00:57에 읽었다. 칭찬카드에도 이전 성공 기록이 남아 있으므로 연결이 처음부터 전혀 동작하지 않았던 경우는 아니다. 이 표는 **조회 당시의 마지막 상태**이며 모든 과거 실패의 원인을 기록한 이력은 아니다.

운영 Vercel의 조사 시점 최근 30분 로그에는 이 학급의 정확한 `GET /task-ledger` 요청 37건이 있었고 모두 HTTP 200이었다. 최근 요청은 약 20초 간격이며 마지막 요청 기록 시각은 14:59:33.492였다. 그 뒤 책스타그램 성공, 0.538초 후 칭찬카드 시간 초과가 저장된 시각과 맞물린다. 외부 요청별 추적 ID와 소요 시간은 남기지 않으므로, **0.538초를 칭찬카드의 정확한 네트워크 대기 시간으로 단정하지 않는다.**

분석한 핵심 파일 9개는 현재 운영 배포의 업로드 원문과 SHA-1이 모두 일치했다. 따라서 과거 계획이나 로컬에만 있는 코드에서 원인을 추측한 것이 아니다.

## 자동 확인과 수동 확인이 다른 이유

| 경로 | 적용 시간 | 여러 게시판 처리 |
| --- | --- | --- |
| 교사 화면 자동 확인 | 전체 처리에 기본 4,000ms 예산 | 앞 게시판 처리에 쓴 시간을 뒤 게시판의 허용 시간에서 차감 |
| 학생 과제 조회 자동 확인 | 전체 처리에 3,000ms 예산 | 같은 방식으로 차감하며 같은 게시판 상태에 기록 |
| 교사의 ‘지금 확인’ | 게시판마다 8,000ms | 앞 게시판에 쓴 시간이 다음 게시판의 8초를 줄이지 않음 |

자동 확인은 시작 시각을 잡고, 게시판별로 `left = budgetMs - 경과시간`을 계산한다. 남은 시간이 500ms 미만이면 그 뒤 게시판 확인을 건너뛴다. 500ms 이상이면 그 짧은 시간을 실제 Padlet 요청의 타임아웃으로 넘긴다. 이 조건 때문에 **아예 건너뛸 때는 새 오류가 없지만, 간신히 시간이 남았을 때 요청을 시작했다가 TIMEOUT을 기록할 수 있다.**

첫 게시판에서 소비하는 시간에는 Padlet 통신뿐 아니라 응답을 과제 상태에 대조하고 DB에 반영하는 처리도 들어간다. 게시판 순서는 화면의 과제 순서가 아니라 `board_id` 정렬로 고정된다. 뒤 게시판이 계속 불리해지는 구조다. 시간 예산은 네트워크 요청 직전의 모든 DB 작업을 포함한 엄격한 전체 종료 시한은 아니므로, 화면 요청의 실제 총시간이 정확히 3초·4초로 끝난다는 뜻은 아니다.

예를 들어 두 번째 게시판의 정상 응답에 1초가 필요해도, 앞 게시판 처리 후 0.6초밖에 남지 않으면 자동 확인은 실패한다. 같은 게시판을 수동으로 확인하면 8초를 기다리므로 성공할 수 있다. **게시판이 고장 나거나 특별히 큰 경우가 아니어도 이 현상이 생길 수 있다.** 이 예시의 응답 시간은 설명용이며 실제 두 게시판의 측정값이 아니다.

근거: `src/server/repositories/configuredPadlet.ts:217–234, 283–286`, `src/server/repositories/database/padletStore.ts:51–58`, `src/server/padlet/padletApi.ts:47–68`.

## 세 과제의 경고가 함께 바뀌는 이유

DB의 오류는 과제 세 개에 각각 저장하지 않고 **학급과 게시판의 조합 한 행**에 저장한다. 과제 목록을 만들 때 같은 게시판의 마지막 성공 시각과 오류를 연결된 모든 과제에 복사한다.

또한 개별 과제 화면에서 누르는 ‘지금 확인’도 내부적으로는 **학급에 연결된 모든 게시판**을 확인한다. 사용자가 칭찬카드 하나에서 눌러도, 해당 게시판 조회가 성공하면 칭찬카드 세 과제의 공통 오류가 지워진다. 수동 확인은 책스타그램 게시판도 다시 읽는다. 세 과제를 연결했다고 매번 같은 게시판을 세 번 요청하는 구조는 아니다.

자동 확인은 교사 화면이 보이는 동안 20초 간격, 포커스 복귀, 학생 과제 조회 등에 의해 시작된다. 별도의 Padlet 예약 작업이 없어도 화면이 열려 있으면 재발할 수 있다. 학생 쪽 요청이 먼저 조회 차례를 얻으면 학생 경로의 더 짧은 예산으로 남긴 결과를 교사도 보게 된다.

근거: `configuredPadlet.ts:119–146, 217–234`, `padletStore.ts:126–150`, `src/server/repositories/database/taskLedger/commands.ts:159–168`, `src/components/tasks/ledger/PadletLinking.tsx:82–95`, `useTaskBoard.ts:102–109`.

## 표시 문구와 실제 영향

과제 목록은 구체적인 오류 코드를 구분하지 않고 모두 **‘패들렛을 읽지 못함’**으로 표시한다. 상세 화면의 `TIMEOUT` 설명은 ‘Padlet이 늦게 답해요’지만, 목록에서는 시간 초과인지 키·권한 문제인지 알기 어렵다.

현재 코드에서 외부 조회가 실패하면 오류만 새로 기록한다. 이전 성공 시각·요약과 이미 반영된 과제 단계는 이 실패 때문에 삭제하거나 되돌리지 않는다. 다만 **다음 확인이 성공할 때까지 새 게시물의 완료 가능 반영이 지연될 수 있다.**

Padlet 조회 실패는 처리 가능한 보조 기능 오류로 저장되고 과제 목록 API 자체는 정상 응답한다. 따라서 이번처럼 HTTP 200 로그만 보면 문제가 없는 것처럼 보일 수 있다.

근거: `src/components/tasks/ledger/TaskLedgerPanel.tsx:55–57`, `src/lib/padletLinkApi.ts:9–18`, `configuredPadlet.ts:92–116`, `padletStore.ts:136–150`.

## 다른 가능성과 판단 범위

- **키 오류·유료 요금제·게시판 권한:** 이번 저장 코드는 이에 해당하는 `INVALID_KEY`, `NOT_PAYING`, `NOT_ADMIN`이 아니라 `TIMEOUT`이다. 같은 키로 책스타그램이 정상이고 칭찬카드의 성공 기록도 남아 있다. 키를 다시 입력하거나 게시판 공개 범위를 넓혀야 한다는 근거는 없다.
- **요청 횟수 제한:** Padlet은 IP당 분당 250요청과 초과 시 1분 대기를 안내한다. 해당 오류는 `RATE_LIMITED`로 구분되므로 이번에 관측한 실패와 다르다. 다만 현재 CRS는 이 오류에도 별도 대기 정책을 두지 않아 향후 보완 대상이다. [Padlet 오류 및 호출 제한](https://docs.padlet.dev/reference/error-handling)
- **칭찬카드의 게시물 수나 첨부파일:** 현재 클라이언트는 `include=posts,sections`로 매번 게시물·섹션 데이터를 읽는다. 공식 문서도 이 방식으로 관련 전체 데이터를 포함한다고 설명한다. 양이나 응답 속도가 영향을 줄 수 있지만, **이번 조사에서 실제 게시물 수·응답 바이트·두 게시판의 독립 응답 시간을 측정하지 않았으므로 칭찬카드가 더 크거나 느리다고 단정하지 않는다.** 첨부 사진 원본을 모두 다운로드한다고도 볼 수 없다. [Padlet 게시판 조회 API](https://docs.padlet.dev/reference/get-board-by-id)
- **페이지 누락 또는 200개 제한:** 현 연결 기능은 새 `padletApi.ts`를 쓰며 8,000,000바이트 상한이 있다. 옛 `padletClient.ts`의 제한과 혼동하면 안 된다. 현재 사용하는 공식 게시판 endpoint에는 페이지 순회를 요구하는 근거가 없고, 이번 오류도 크기·형식 오류가 아닌 시간 초과다.
- **수동·자동 요청의 경합:** 새 성공보다 늦게 끝난 과거 자동 실패가 오류 상태를 덮을 여지도 있다. 결과에 시도 번호를 대조하는 보호가 없기 때문이다. 다만 이번 개별 실패에서 실제로 이 경합이 발생했다는 기록은 없으므로 부가적인 취약 지점으로 구분한다.

게시판 확인 순서와 자동 시간 예산, 실제 `TIMEOUT`은 확인했다. 어느 요청에서 첫 게시판의 통신과 DB 처리에 각각 몇 ms를 썼는지, 칭찬카드 자체의 정상 응답 시간이 얼마인지는 현재 기록만으로 분리할 수 없다.

## 실제 서비스 코드를 사용한 격리 재현

제품 코드를 수정하지 않고 `createPadletService`와 격리 PGlite의 실제 스키마·저장·과제 처리를 사용했다. 두 게시판에 과제를 세 개씩 연결하고, 외부 통신과 시계만 결정론적으로 대체했다. **교사 경로와 학생 경로 두 조건 모두에서 문제 현상을 재현했다.**

| 재현 조건 | 전체 자동 예산 | 첫 게시판의 가정한 응답 시간 | 두 번째의 가정한 응답 시간 | 두 번째에 실제 전달한 제한 |
| --- | --- | --- | --- | --- |
| 교사 자동 확인 | 4,000ms | 3,400ms | 1,000ms | 600ms → TIMEOUT |
| 학생 자동 확인 | 3,000ms | 2,400ms | 1,000ms | 600ms → TIMEOUT |

같은 응답 조건에서 수동 확인은 두 게시판에 각각 8,000ms를 주어 모두 성공했고, 이후 자동 확인은 다시 같은 세 과제에 TIMEOUT을 표시했다. 마지막 성공 기록과 과제 단계가 유지되는 것도 확인했다. **뒤 게시판 자체가 앞 게시판보다 빨라도 남은 시간 제한 때문에 실패할 수 있다.**

이는 실제 서비스의 시간 배분·오류 저장·과제별 상태 전파를 검증한 재현이다. 표의 응답 시간은 주입한 값이며 실제 Padlet 속도나 HTTP 취소 타이머 측정값이 아니다. 외부 요청과 운영 데이터 변경은 0건이고 Git HEAD·인덱스·추적 파일 바이트는 실행 전후 같았다. 최초 실행 준비와 합성 시계 설정의 실패 기록은 각각 보존했고, 수정한 격리 검사는 최종 2개 모두 통과했다.

## 수정 방향

1. **게시판별 조회 시간과 과제 화면 응답 시간을 분리한다.** 뒤 게시판에 앞 게시판이 쓰고 남은 짧은 시간을 주지 않도록 한다. 충분한 개별 조회 시간, 제한된 동시 처리 또는 순서를 공정하게 분배하는 독립 동기화가 필요하다. 화면의 전체 대기 시간만 크게 늘리면 과제 목록 자체가 느려질 수 있다.
2. **예산 부족과 외부 장애를 구분한다.** 이번 주기에 확인을 보류한 상태, 응답 시간 초과, 키·권한 오류를 서로 다르게 표시하고 마지막 정상 확인 시각을 함께 보여준다. 경고만 숨겨서 새 게시물이 반영되지 않는 문제를 가리면 안 된다.
3. **보드별 진행 중 요청과 결과 순서를 관리한다.** 자동·수동 요청이 겹쳐 오래된 실패가 새 성공을 덮지 않도록 한다. 요청 제한에는 별도 대기 시간을 적용한다.
4. **운영 측정과 회귀 검사를 보강한다.** 자동/수동/학생 경로, 게시판 순서, 주어진 타임아웃, 외부 소요 시간, HTTP 상태, 응답 바이트만 기록한다. 게시물 본문·학생 이름·API 키는 로그에 남기지 않는다. 다중 게시판과 지연 응답, 자동·수동 경합을 검사한다.

- 요청 시각: `request-timeline-redacted.json`. 경로가 정확히 일치하는 37개 요청 기준이며 하위 경로를 포함한 집계와 구분한다.
- 격리 재현: `padlet-budget-reproduction.json`, `padlet-budget-vitest.json`, `repro-execution.json`. 최초 실행 준비·합성 시계 설정 실패는 `repro-attempt-1`, `repro-attempt-2`에 별도 보존했다.
- 직접 Padlet API 측정 준비는 필요한 앱 암호화 키가 로컬 파일에서 비공개 처리돼 외부 요청 전에 종료됐다. 이 준비 실패를 Padlet 통신 실패로 계산하지 않았다.
- 제품 코드·DB·연결 설정·배포는 변경하지 않았다. 이 분석 문서와 격리 조사 자료만 추가한다.
