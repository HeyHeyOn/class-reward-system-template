# CRS 계정·결제·성장 기능 보안 및 성능 조치 결과

작성일: 2026-10-11 · 상태: **운영 배포·DB·권한·운영 확인 및 구현 코드 푸시 완료**

[10월 11일 심층 감사](2026-10-11-crs-system-security-performance-audit.md)의 11개 조치 항목을 수정하고, 관련 조회·잠금·초기 화면 로딩을 개선했다. v3의 539파일 전체 실행은 **31,687개 통과·122개 실패·913개 건너뜀**으로 종료됐으며 원본 감사는 REJECTED로 보존했다. 실패 원인에 해당하는 테스트 픽스처와 경로 목록만 수정한 v5에서 7개 파일 전체 358개를 다시 통과시켰다. 소스가 같은 나머지 532개 파일과 정확한 사례 목록을 연결한 합성 감사 결과는 **31,815개 통과·913개 미실행/차단**이다. 이는 **단일 전체 실행의 통과가 아니다.** 별도 네이티브 12파일 78개 및 정적·배포 입력·후보 HTTP 확인을 통과했고, 운영 DB 0051·0052·0053 적용을 확인했다. 운영 DB 소유자 연결의 함수 생명주기 검사·앱 권한 카탈로그 확인, 운영 도메인 승격, 기존 함수 9개의 권한 회수, 운영 HTTP 34개와 실제 Google 로그인까지 확인했다. 직접 runtime 자격 증명 연결 검증과는 구분한다. 구현 커밋 4개를 정상 푸시했고 `ls-remote`가 `dac638999959777e26dcee65fcbf5bf082fa1da2`와 일치함을 확인했다. 이 보고서는 별도 문서 커밋으로 같은 브랜치에 보관하며, 문서까지 포함한 최종 원격 HEAD 확인은 `release-v5/final-git-verification.json`과 단일 진행 기록에 남긴다.

운영 진입점은 **https://crs.hwanit.com/classes 를 유지**한다. 새로운 서버 관리 세션이 없는 기존 교사 쿠키는 거부하므로, 기존 교사는 **한 번 Google에 다시 로그인**해야 한다. 학급·학생 데이터를 새 서비스로 옮기는 작업은 아니다.

탈퇴 처리는 명확히 달라진다. 소유 학급의 학생·거래·과제·성장·보관함·이전 원본 자료를 같은 트랜잭션에서 즉시 파기하며, **탈퇴한 학급과 기록은 서비스에서 복구할 수 없다.** 일반 학급 휴지통과 회원 탈퇴를 구분하고, 탈퇴 확인 화면과 개인정보처리방침에 이를 안내한다.

불확실한 결제 복구 기록은 학급 API 경로별 `sessionStorage`에 최초 POST 전에 저장하고 다시 읽어 확인한다. 작업 ID·학생 번호·상품·가격 조건·교환권만 남기며 QR 인증값·학생 이름·잔액·성공 응답은 저장하지 않는다. 같은 학생의 QR을 다시 읽어 기존 요청을 확인한다. 최대 문자열 길이 128×1,024, 유효 기간 7일로 제한하며, 손상·만료·저장 실패에서는 기록을 지우고 새 결제를 만드는 대신 결제를 차단한다. **탭 종료 뒤의 보존은 sessionStorage의 보장 범위가 아니다.**

## 추가로 발견한 탈퇴와 학급 작업의 경합

초기 수정은 요청 입구에서 세션을 확인했지만, 확인 뒤 탈퇴가 먼저 완료되면 이미 통과한 학급 생성 요청이 같은 Google subject의 계정과 학급을 다시 만들 수 있었다. 학급 관리·사용 시작은 학급 행을 먼저 잠그고 사용자 행을 잠갔고, 탈퇴는 사용자→학급 순서여서 교착도 가능했다.

0051의 인증된 CREATE·MANAGE·START 래퍼는 **계정 세대 행을 먼저 잠그고 세션·동의를 재확인한 상태로 전체 변경을 실행**한다. XLSX 가져오기에서 새 학급 사용을 시작하는 경로도 같은 신원과 잠금 순서를 사용한다. 탈퇴가 먼저 끝나면 대기 중인 작업은 인증 오류로 거절된다. 반대로 복제가 먼저 끝나면 탈퇴가 새 복제 학급까지 포함해 정리한다. 학급 생성·시작·관리의 기존 subject-only 함수는 내부 구현으로 남기되 최종 앱 역할의 직접 실행 권한을 회수한다.

배포 전후의 구버전 요청도 고려했다. 0053의 기존 탈퇴 함수 자체가 계정 세대 잠금을 먼저 잡고, 파기 후 해당 계정의 모든 교사 세션을 삭제하고 세대를 교체한다. 따라서 구버전 탈퇴 진입점이 잠시 남아 있어도 새로 발급된 서버 세션을 폐기하지 못하는 간극을 막는다. 이 보완을 포함한 최종 후보 회귀 결과는 아래 운영·출시 확인 표에 별도로 기록한다.

## 자료 이전 HTTP의 추가 인증 경계

마지막 교차 검토에서 freezing의 동의·시작·재획득 HTTP 9개 진입점이 기존 쿠키와 자료 이전 전용 조건만 검사하고, 새 DB 교사 세션의 폐기 여부와 현재 약관 동의를 확인하지 않는 간극을 발견했다. v3는 **신뢰된 학급 요청 문맥 → 유효한 DB 교사 세션·현재 동의 → 기존 자료 이전 검증** 순서를 적용한다. 학급 문맥이 없는 직접 라우트 호출은 세션 SQL이나 자료 이전 처리기를 실행하기 전에 거절한다. 정상 학생 세션·공개 기능과 legacy Sheets의 기존 신원 처리는 유지한다.

실제 9개 라우트와 학급 dispatcher를 연결한 신규 11개 검사에서 로그아웃·만료·과거 형식 쿠키·동의 누락/구버전·충돌한 대기 신원·미로그인을 거절하고, 유효한 세션은 기존 하위 검증까지 도달함을 확인했다. 이 검사는 DB 세션 검증을 실제로 실행하되 하위 자료 이전 효과는 대체한다. 별도로 기존 시작 흐름의 비학급 직접 호출 거절 1개도 선별 통과했다. 신규 11개와 겹치는 범위를 합산한 총 통과 수는 만들지 않는다.

기존 자료 이전 테스트 네 파일의 인증 픽스처는 실제 DB `begin+AGREE`로 발급한 세션을 사용하도록 바꿨다. 원인 확인용 선별 실행 후, 종료된 v3 전체 회귀에서 `freezingReacquisitionIntake` 71개, `freezingReacquisitionCentralProduction` 35개, `startFreezingFlow` 28개가 각 파일 전체 통과했다. 이 결과는 아래 v5 합성 감사에서 변경 없는 원본 모듈로 대조했다. 원본 전체 실행 자체는 실패로 유지한다. v1의 최초 71개 실패에 대한 픽스처 원인 추적과, 실제 제품의 9개 HTTP 인증 누락 보완을 같은 결과로 취급하지 않는다.

## 조회·성장 처리·화면 로딩 개선

### 펫 현재 상태와 이력 분리

은행의 일반 펫 새로고침에서 졸업 펫 전체 목록을 내려주지 않는다. 기존 DTO의 `dex` 필드는 호환 형태로 남기되 빈 배열을 반환하며, 현재 화면은 별도 도감 API를 사용한다.

- 도감을 열 때만 `/api/c/[slug]/bank/me/pet/dex`를 호출하고 **24개씩** 더 읽는다. API는 확인된 학생 세션의 본인 이력만 조회하며 임의 학생·페이지 크기 입력을 받지 않는다.
- 페이지 경계는 졸업 시각의 **마이크로초와 펫 ID**를 함께 사용한다. 커서는 학급·학생에 묶이고, 같은 시각의 여러 졸업 기록도 빠지거나 중복되지 않게 한다.
- 종·색 수집 현황은 페이지 밖 기록도 반영하도록 최대 **28개 조합의 최신 대표**를 인덱스로 찾는다. 방의 동반 펫은 최대 두 개 ID의 기본 키 조회로 읽으며, 첫 페이지에 없는 동반 펫도 돌려보낼 수 있다.
- 최근 FEED는 전체 이력의 집계 대신 일치하는 부분 인덱스에서 최신 한 행을 읽는다. 기능이 꺼져 있으면 설정 조회 뒤 기본 상태를 반환하고 불필요한 이력 조회를 생략한다.
- 도감의 더 보기 실패는 이미 읽은 목록과 커서를 유지한다. 닫힌 화면의 늦은 응답은 버린다.

합성 졸업 이력 1,000개·과거 FEED 1,000개에서 전체 페이지 순서와 기존 DB 정렬 결과의 일치, 중복·누락 없음, 제한된 앱 역할의 인덱스 사용을 확인했다. 이는 해당 경로의 반환량과 조회 계획 검증이며 모든 성장 조회가 이력과 무관한 상수 비용이라는 주장은 아니다.

### 성장 훅의 설정 재사용과 잠금 유지 시간

한 트랜잭션 안에서는 성장 기능 존재 여부와 나무·펫 설정을 재사용한다. 교사 일괄 완료의 성장 훅은 계좌·과제·작업 기록 처리를 마친 뒤 **커밋 전에 원래 이벤트 순서대로** 실행한다. 나무→펫의 기존 순서와 같은 트랜잭션의 원자성을 유지하면서 공유 나무 잠금을 잡은 뒤 수행하는 부수 작업을 줄인다. 보상 취소 훅도 같은 원칙으로 옮겼다.

학생 세 명·나무 목표 두 번의 합성 검사에서 기능 확인 1회, 나무 설정 1회, 펫 설정 1회를 확인했다. 나무는 목표에 도달한 두 건까지만, 펫은 세 건 모두 성장했고, 동일 작업 재시도는 중복 지급하지 않았다. 취소 후 나무·펫·과제 상태의 되돌림도 검사했다. 운영 잠금 대기 시간이나 다학급 처리량 개선률을 측정한 것은 아니다.

### 화면 코드 분리와 요청 본문 제한

은행 홈의 작은 나무·펫 카드를 상세 화면 모듈에서 분리했다. 상세 화면은 `next/dynamic`으로 해당 화면 진입 시 불러오며, 펫 카드의 그림 모듈도 별도로 로드한다. 홈 카드가 그려야 하는 나무 캔버스 코드는 공용으로 남는다. 운영 은행 페이지의 비인증 초기 HTML이 참조하는 script 11개의 비압축 합계는 배포 전 **786,534바이트에서 704,233바이트로 82,301바이트(약 10.46%) 감소**했다. 두 시점 모두 script 개수는 11개다. 이후 동적 import는 제외한 측정이며, 압축 전송량·전체 다운로드량·실제 화면 표시 시간이나 전체 속도 개선률을 뜻하지 않는다.

공통 `readBoundedRequestText`는 실제 스트림 바이트를 읽는 동안 제한을 확인한다. 길이 헤더가 없거나 실제보다 작아도 제한을 적용하고, 인코딩된 요청·잘못된 길이·잘못된 UTF-8을 거절한다. 한도를 넘으면 원본 스트림을 취소하되 취소 완료를 무한히 기다리지 않는다. 계정 1,024바이트, 학급 변경 2,048바이트, 나무 10,000바이트, 펫 20,000바이트 제한을 각 처리기에 적용했다. 여러 청크로 나뉜 정상 한글은 허용한다.

## 개인정보 파기의 DB 경계

0053은 삭제 예외를 일반 관리자 권한이나 요청에서 설정할 수 있는 값으로 열지 않는다. 소유자 권한 함수가 탈퇴 기록과 연결된 **백엔드·트랜잭션·학급별 비공개 문맥**을 만들고, 해당 트랜잭션의 닫힌 학급에 한해 보호 행의 DELETE를 허용한다. 평상시 장부 UPDATE/DELETE 차단과 일반 휴지통 복원 기능은 유지한다.

85개 tenant 자료 테이블을 FK 순서로 파기하고, 학급의 예전 주소도 내부 폐기 주소로 바꾼다. 운영 스키마 목록과 정적으로 대조했을 때 대상 누락과 FK 삭제 순서 충돌은 없었다. 새로운 tenant 자료 테이블이 추가됐는데 파기 목록에 없으면 **전체 탈퇴를 실패·롤백**시킨다. 중간 삭제 실패도 계정·세션·학급을 일부만 지운 상태로 남기지 않는다.

탈퇴 처리 내부 번호·시각, 폐기된 로그인 및 중복 보상 재사용 방지용 해시는 보안 목적의 최소 기록으로 남긴다. 일반 앱 역할은 파기 문맥·잔여 파기 함수·교사 세션 표를 직접 읽거나 쓸 수 없다. 과거 탈퇴 자료를 위한 운영자 전용 파기 함수는 제공하지만, **0053 설치만으로 과거 기록을 자동 정리하지는 않는다.** 이번 운영 적용 전후 조회에서 과거 탈퇴 정리 대상 계정·학급이 모두 0건임을 확인해, 과거 사용자 자료를 추가 파기한 건은 없다.

개인정보처리방침과 탈퇴 확인 문구는 즉시 파기·복구 불가 및 최소 보안 기록을 설명하도록 수정했다. 법적 안내의 새 개정은 코드상 **2026-10-18 시행**으로 등록해 사전 안내와 시행 후 재동의를 구분한다. 서비스 DB의 즉시 파기와 별도 백업 보존 기간은 같은 의미가 아니며, 이 문서는 백업 업체의 실제 삭제 완료를 새로 검증했다는 뜻이 아니다.

## 기존 자료 이전 경로의 호환성 보완

전체 회귀 준비 중 기존 로컬 자료 이전 검사 두 파일의 **85개 중 22개 실패**를 먼저 재현했다. 그중 21개는 0042 트리거가 정상 이전 데이터에도 만드는 `task_history_prefixes`·`task_history_entries`를 기존 재시도 검사가 알 수 없는 점유 테이블로 거절한 문제였다. 나머지 한 개는 현대 BANK 경로를 실행하는 테스트 DB에 0041이 빠져 현재 상태 테이블을 찾지 못한 픽스처 문제였다. 이 최초 결과는 수정 후 통과 결과로 덮어쓰지 않고 보존했다.

`localCandidateMaterialization.ts`와 `localMaterializationRunner.ts`는 이력 캐시 세 표만 명시적으로 허용하고, SELECT 권한을 필수로 확인한 뒤 각 행의 내용까지 해시로 묶어 재시도 영수증과 대조한다. 원본 캐시는 검증된 학급과 과제 범위에 한정한다. 다른 학급·알 수 없는 표·비공개 데이터의 섞임과 예상하지 않은 체크포인트는 계속 거절한다. 캐시를 이전 입력이나 활성화 권한으로 승격하지 않으며, 이 검사가 캐시 내용의 모든 계산 의미까지 재검증한다고 주장하지 않는다. 캐시 정보가 없는 과거 합성 영수증은 조용히 보정하지 않고 새 후보를 요구한다.

테스트 DB는 현재 마이그레이션과 실제 런타임 권한에 맞췄다. 수정 후 PGlite 대표 6개와 BANK·정확한 재시도 1개, 네이티브 대표 3개가 각각 통과했고, v3 전체 실행에서 `localCandidateMaterialization.test.ts`의 현재 65개 모두 통과를 확인했다. 선별 실행은 행 수가 같은 캐시 변조, SELECT 권한 누락, 원본 보존과 읽기 전용 캐시 권한을 포함한다. 중간 실행에서 발견한 조정 행 권한 누락도 픽스처에서 수정했으며 그 실패 로그를 보존했다. **최초 85개 중 22개 실패 기록을 유지하며, 선별·파일별 통과를 최종 전체 회귀의 통과로 환산하지 않는다.**

### 이전 후보의 수집 실패·중단과 v3 재실행

고정 후보를 별도 디렉터리로 복사한 첫 사전 수집은 테스트 파일 9개에서 `.git/index`가 없어 실패했다. 이 파일들은 제품·테스트 원문 및 Git 인덱스가 실행 전후 바뀌지 않는지 검사하며, 테스트 모듈을 불러오는 단계부터 인덱스를 읽는다. 제품 동작을 실행한 뒤 발견된 실패나 9개 테스트 사례의 단언 실패로 계산하지 않는다.

후보 디렉터리에 독립된 Git 인덱스를 마련했고 제품·테스트 소스 바이트와 원본 저장소 인덱스는 바꾸지 않았다. 최초 `collection-initial-failure.json`·로그를 보존한 채 v1 본 검사를 시작했다. 그러나 위 HTTP 인증 누락 때문에 제품 코드와 후보를 교체해야 해서 **v1은 미완료·승인 불가로 중단**했다. 중단 기록의 완료 파일 수는 7개이며, 그때까지 사례 상태는 통과 5,280개·실패 71개·건너뜀 10개가 관측됐다. 이는 종료 전 부분 관측값이며 전체 결과가 아니다. 종료 코드는 143이고 고정 소스와 인덱스의 불변을 확인했다. 실행 속도 때문에 중단한 것이 아니며, **v1 부분 통과에서 최종 출시 검사로 인정한 건수는 0개**다.

v2는 전체 회귀를 시작하지 않은 채 폐기했고, 신뢰된 학급 문맥을 먼저 확인하는 최종 순서까지 반영한 v3로 교체했다. v3는 이전 부분 통과를 이어받지 않고 **539개 테스트 파일 전체를 새로 실행**했다. 모듈 실행 전 선언 목록을 기록하고 종료 후 파일·이름·건너뜀 근거를 대조한다. 목록 검사 실패에 이어 합성 인증 픽스처에서도 추가 실패가 관측됐지만 원본 실행을 끝까지 유지했다. 종료 결과는 **539파일·32,722사례 중 31,687개 통과·122개 실패·913개 건너뜀**, 종료 코드 1이다. 파일·선언·JSON·실행 journal의 사례 다중집합과 소스 불변을 확인했으며, 원본 `full-audit.json`과 `skip-audit.json`은 **REJECTED로 그대로 보존**했다.

### 중간 후보 v4의 목록 보완과 v5 재검증 범위

v3의 `legacyWriteFreezeRoutes.test.ts`에서 실제 API 전체 목록과 테스트 JSON을 비교하는 검사 1개가 실패했다. 새 `GET /api/bank/me/pet/dex`가 실제 라우트·인증 및 `TENANT_ROUTE_INVENTORY`에는 등록됐지만, 별도의 테스트 JSON에는 빠져 **131개 대 132개**가 된 원인이었다. 제품의 도감 인증 누락과 구분한다.

커밋 `502c226fb81942039144ed9b4bdab9a07e674d77`은 `src/server/testing/legacyWriteFreezeRoutes.json`에 `student-session-read` 항목을 넣고, `src/server/legacyWriteFreezeRoutes.test.ts`의 기대 개수를 132로 수정하며 해당 분류 단언을 추가했다. 이 두 파일만 변경됐다. v3·v4 소스 manifest 1,473개 중 **1,471개는 동일**하며 제품 런타임 코드는 바뀌지 않았다. 다만 JSON 한 개는 실제 업로드 입력이므로, 두 후보의 모든 배포 입력이 같다고 주장하지 않는다.

처음에는 이 JSON을 소비하는 `legacyWriteFreezeRoutes.test.ts` 157개와 `legacyWriteFreezeReads.test.ts` 20개를 전체 재검증하고, 변경 없는 537개 모듈과 독립 종합 감사로 연결하려 했다. 그러나 **추가 인증 픽스처 실패가 확인돼 두 소비 파일만 재검증하면 된다는 전제는 철회했다.** v5에서 아래 다섯 인증 픽스처 파일을 추가로 수정하고, 전체 7개 소비 파일을 재검증하는 범위로 확정했다. v4를 그대로 전체 검증 통과로 취급하지 않는다.

### v5 합성 회귀와 미실행 분류

v3→v5의 manifest 1,473개 경로는 같으며, 변경은 정확히 **7개 경로**뿐이다. 위 목록 JSON·검사 외에 `studentDeletionRoutes.test.ts`, `taskLedgerRoutes.test.ts`, `currentPreflight.acceptanceBoundary.test.ts`, `identityLifetime.test.ts`, `historicalConflictLink.boundary.test.tsx`의 인증 픽스처를 수정했다. 기존 합성 쿠키가 새 DB 세션·동의 검증에서 거절된 원인에 맞춰 신원을 보완했고, identity lifetime의 대기 검사는 요청이 먼저 거절됐을 때 진입 대기를 계속하지 않도록 했다. 실제 제품 인증 조건은 완화하지 않았다. 검토한 **122개 실패의 파일·전체 이름·오류**를 별도 근거에 고정했다.

수정된 테스트 6개와 JSON의 추가 소비 파일 `legacyWriteFreezeReads.test.ts`까지 **7개 파일 전체 358개**를 필터 없이 다시 실행해 모두 통과했다. 기존 352개 사례의 다중집합은 하나도 삭제·개명하지 않았고, 폐기된 교사 세션 거절 6개만 추가했다. 변경 없는 **532개 모듈**은 원본 실행 결과를 재사용했다. 독립 합성 감사의 110개 조건은 소스·목록·실행 순서·정확한 사례 Counter·122개 실패의 대체·skip을 검증했다. 결과는 **총 32,728개 = 통과 31,815개 + 건너뜀 913개**이며, 교체한 원본 7개 파일의 통과 사례를 재실행 결과에 중복 더하지 않았다. `mode=composite`, `originalFullRunPassed=false`, `singleCleanFullRun=false`를 고정한다.

기본·합성 회귀에서의 913개 건너뜀은 **환경 선택 실행 미실행 910개와 기존 차단·미검증 3개**다. 별도 네이티브 실행은 이 원본 skip 상태를 바꾸거나 합성 통과 수에 더하지 않는다. 차단 3개는 실제 브라우저의 이전 이력 다운로드 경계, 전체 이전 범주의 최종 원본·대상 대조, 기존 복원 픽스처의 비슈퍼유저 테이블 소유자 격리이며 이번에 검증 완료로 처리하지 않았다. 최초 skip 감사의 예상 밖 1개는 `localRestoredPreparedCandidate.postgres.test.ts`가 정적으로 가져온 `Task19 isolated restored candidate child`였다. 실제 전체 실행의 네 환경 변수에는 `TASK19_CANDIDATE_REQUEST`가 없으므로 helper의 `it.skipIf(!path)`가 이 정확한 사례 1회를 건너뛴다. 기존 909개 분류 및 부모 suite 규칙에 포함되지 않은 imported child이며, 네이티브 부모가 요청 파일을 지정해 별도 프로세스로 실행하는 경로와 구분한다. importer·helper 해시와 선언 위치에 묶인 보충 검토만 추가하고 원래 inventory·감사 결과를 수정하지 않았다. **913개를 통과 수에 포함하지 않으며, 차단된 3개를 검증 완료로 바꾸지 않는다.**

첫 합성 감사는 입력 대조를 마친 뒤 비정상 유니코드 `U+D800`을 포함한 테스트 이름의 해시 직렬화에서 실패했다. 그 결과의 `accepted=false`와 당시 코드를 `composite-attempt-1`에 원문 해시와 함께 보존했다. JSON의 ASCII escape 직렬화 한 줄만 바꿔 정확한 문자열·Counter·조건을 유지한 재감사를 통과시켰으며, 입력 증거 30개의 전후 해시가 같음을 확인했다. 첫 실패를 통과로 덮어쓰지 않았다.

### 소스 동일성 및 운영 승격 확인

최종 검증 소스 v5의 manifest SHA-256은 `96832605357061155b09aec5065185c64d626636e5977a82bd500a38b1c1371c`이며, 테스트 픽스처 보완까지 반영한 커밋은 `dac638999959777e26dcee65fcbf5bf082fa1da2`다. 프로덕션 후보 `dpl_6vHF5Bd1XAewPhHhNybkZcBJxiTT`는 READY다. v4 이후 바뀐 다섯 파일은 배포에서 제외하는 테스트뿐이므로, **v4·v5의 실제 업로드 입력 736개가 원문 그대로 같음**을 확인해 이미 빌드한 후보를 재사용했다. v5 기준 원격 736개 입력의 SHA-1도 다시 대조했다. v3→v4에서는 목록 JSON 한 개가 실제 업로드에서 바뀌었으므로 세 후보 전체가 같다는 뜻은 아니다.

v5와 위 Git 커밋의 비교에서 소스 734개 중 **694개는 원시 바이트가 같고, 40개는 CRLF/LF 줄바꿈만 다르다.** 기존 `core.autocrlf=true`의 Git 정규화 필터를 적용하면 734개 모두 커밋 내용과 일치한다. 생성 선언 파일 `next-env.d.ts`는 이 커밋 비교에서 분리했다. 따라서 **배포 입력과 원격의 736개 원문 일치**와 **Git 필터 정규화 후 734개 커밋 일치**를 구분한다. 앞선 v3의 최초 `committed-source-audit.json` 실패와 줄바꿈 원인 분석도 보존했으며, Git 원시 바이트가 모두 일치했다고 바꾸지 않는다. 컴파일 산출물의 독립 재현을 증명한 결과도 아니다.

v5에 연결한 후보 점검에서 공개 페이지·비인증 API 거절·자료 이전 인증 경계·미리보기 차단·로그아웃 쿠키 등 **33개 HTTP 점검**과 보안 헤더를 확인했다. 임시 우회 키 회수 후 잔여 키는 0개이고, 보호 설정과 기존 운영 도메인 연결을 유지했다. v1·v3 점검 수를 더하지 않는다. 이 33개는 승격 전 후보 점검이며, 아래 승격 후 운영 HTTP 34개와 합산하지 않는다.

운영 DB 읽기 전용 사전 점검에서 과거 탈퇴 파기 대기는 0건이었다. 이후 `database-migration-verification.json`으로 **0051·0052·0053 적용과 커밋 완료**를 확인했다. 새 함수의 소유자 권한·고정 search path·PUBLIC 실행 차단, 세 비공개 테이블의 FORCE RLS와 앱 직접 접근 차단, 펫 인덱스 세 개의 정의·준비·유효 상태를 확인했다. 과거 탈퇴 대기 계정·학급은 모두 0건이었다. 설치 단계에서는 구버전과 공존할 추가 권한을 먼저 적용했고, 아래 검증·승격을 거쳐 최종 권한으로 전환했다.

운영 DB 함수 검증은 **소유자 자격 증명으로 연결해 SECURITY DEFINER 함수 생명주기와 runtime ACL 카탈로그를 확인**하는 방식이었다. 세션 발급·동의·학급 생성·탈퇴·폐기 세션 거절을 합성 신원으로 실행하고 전체 트랜잭션을 롤백했다. 대상 DB와 유효 소유자 역할을 단계마다 확인했다. **실제 runtime 자격 증명 연결 및 해당 연결에서의 권한 거절 쿼리는 실행하지 않았다.** 실제 제한된 역할·RLS 동작을 검사한 격리 네이티브 12파일 78개와 이 운영 검증을 구분한다. 최초 연결 검증은 Vercel이 비밀 환경값을 `[SENSITIVE]`로 반환해 DB 접속 전에 중단됐다. 두 번째 소유자 연결의 역할 전환은 현재 역할 설정의 `SET` 제한으로 거절됐으며 롤백했다. 두 실패의 원문 결과와 검증기를 `runtime-attempt-1`, `runtime-attempt-2`에 보존한 뒤 위 범위로 검증했다. 앱 비밀번호나 역할 상속 권한을 변경하지 않았다.

`promotion-verification.json`에서 기존·현재 도메인의 연결이 검증한 배포 `dpl_6vHF5Bd1XAewPhHhNybkZcBJxiTT`로 바뀌었음을 확인했다. 이어 `final-acl-verification.json`에서 기존 subject-only 계정·학급 변경 및 내부 잠금·파기 **9개 함수의 runtime·PUBLIC 실행 권한 회수와 커밋**을 확인했다.

승격 후 **운영 HTTP 34개**, 보안 헤더, 관리자 쿠키 만료, 옛 도메인의 경로·쿼리 보존 리다이렉트를 확인했다. 상품 목록의 별도 `cache=MISS` 응답으로 배포된 앱의 실제 학급 조회와 PostgreSQL 읽기도 확인했다. 보호 설정과 다른 프로젝트 4개의 연결은 유지됐고, 잔여 우회 키는 0개였다. 이 읽기 확인이 교사 변경·학생 결제 전체 경로의 운영 검증을 뜻하지 않는다.

실제 Chrome에서 기존 운영 Google 계정을 선택하고 callback을 거쳐 인증된 학급 목록으로 돌아오는 것을 확인했다. 프로필·로그아웃 표시와 학급 대시보드 렌더링까지 확인했으며, 새 약관 동의나 새 권한 요청은 하지 않았다. 이 검사는 실제 OAuth와 배포 앱의 교사 세션 발급·검증을 포함하지만, 프로필 수정·학급 생성/삭제·결제·탈퇴는 포함하지 않는다.

운영 인덱스는 이름만으로 완료 처리하지 않고 정의·준비·유효 상태를 확인한다. 마이그레이션 트랜잭션의 커밋 전 스키마·함수·권한 검증이 실패하면 롤백하고 승격하지 않는 절차를 적용했다. 커밋 뒤의 후속 검사 실패만으로 이미 적용한 마이그레이션이 롤백되지는 않는다. DB 커밋 여부가 불명확한 경우에도 SQL을 무조건 다시 실행하지 않고 카탈로그와 증거를 먼저 대조한다. **이미 성공한 탈퇴의 데이터 삭제는 앱 배포를 되돌려도 복원되지 않는다.** 최종 ACL 적용 뒤에는 구버전이 사용하는 동의·프로필·탈퇴·학급 변경 함수의 실행 권한이 회수되므로, baseline 배포로 도메인 연결만 되돌리는 롤백은 호환되지 않는다. 복구 후보는 현재 성장·보관함·세션 스키마를 이해하는 코드여야 한다.
