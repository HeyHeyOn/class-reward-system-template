여러 검사 묶음에 겹치는 항목이 있으므로 단순 합산하지 않는다. 저장소 전체 회귀 검사를 새로 완료한 것으로 표기하지 않는다. 최초 실패와 재검사 근거를 보관하며 제외·미완료 실행을 통과에 넣지 않는다. 취소 시각 수정 뒤 취소 파일 전체 39건도 다시 통과했다. 전체 TypeScript 검사, 변경 파일 ESLint와 최종 추가 파일 검사, 차이 공백 검사, 고정 후보 Next.js 프로덕션 빌드가 통과했다.

실제 격리 PostgreSQL 17.11에서 학급당 학생 24명·과제 10개로 측정했다. 한 학급은 이벤트 2,400개와 24,000개를 비교하고, 동시 측정은 이 학급과 이벤트 2,400개인 나머지 네 학급이 DB 연결 두 개를 공유했다. 비교하는 모든 학급·이력 길이에서 최종 화면 JSON이 완전히 일치했다.

| 과제 이력 | 가져온 상태 행, 전 → 후 | 단일 조회 중앙값, 전 → 후 | 단일 조회 p95, 전 → 후 |
| --- | ---: | ---: | ---: |
| 2,400개 | 2,400 → 240 | 213.11 → 102.35ms | 303.45 → 254.27ms |
| 24,000개 | 24,000 → 240 | 1,787.81 → 118.17ms | 3,463.20 → 280.68ms |

단일 조회는 방식별 12회다. 다섯 학급 동시 조회의 요청 40개씩을 비교하면 중앙값은 4,208.21 → 635.60ms, p95는 5,982.17 → 1,150.34ms였다. 공유 로컬 호스트·Docker 소켓 중계의 영향을 포함한다. HTTP, 쓰기, 과제 기록 페이지, 운영 최대 수용량을 측정한 값은 아니다.

처음 240,000개 합성 자료는 시드 생성 중 컨테이너 연결 종료로, 다음 67,200개 자료는 명시적인 디스크 공간 부족으로 끝까지 완료하지 못했다. 격리 DB의 저장 공간 제한은 256MiB였다. 제한을 늘리지 않고 최종 33,600개 조건에서 전체 비교와 측정을 완료했다. 미완료 시도의 수치를 성능 결과에 포함하지 않았다. 시험 컨테이너와 임시 파일 제거도 확인했다.

## 운영 반영

운영 DB에 0041·0042를 같은 트랜잭션으로 적용했다. 원본 과제·학생·부여·완료·작업 표의 행 수와 전체 내용 지문을 적용 전후 비교하여 변경 없음을 확인했다. 현재 과제 8개의 화면 데이터를 기존 전체 이력 계산과 대조했고, 과제 기록 918건을 23페이지로 읽어 기존 타임라인과 마이크로초까지 일치함을 확인했다. 기존 목록의 ID만 표 간 충돌 방지를 위한 새 식별 형식으로 정규화했다.

기준 시점 이후 원본 이벤트 160개와 체크포인트 160개의 대조에서 누락·고아·메타데이터 불일치·단계 계산 불일치는 모두 0개였다. 새 표 네 개의 FORCE RLS·앱 SELECT 전용 권한과 보수 함수 12개의 고정 search_path·공개 실행 차단을 실제 운영 DB에서 확인했다. 이 변경에서 앱 계정 비밀번호로 운영 DB에 다시 접속한 것은 아니며, 앱 역할을 통한 실행·동시성·권한 검증은 별도 실제 PostgreSQL에서 수행했다.

배포 후보 `dpl_9dwcXPcPn7jtxyrKKN95Wfc38Lb2`는 haeon0511 프로젝트, Singapore `sin1`에서 READY 상태다. 후보 619개 소스 파일의 해시와 배포 메타데이터가 일치하며, 저장소 대조의 예외는 자동 생성되는 `next-env.d.ts`의 프로덕션 타입 경로와 최종 Git 정리 때 제거한 `sheetsSettingsRows.ts` 끝의 빈 줄 한 개다. 뒤의 파일은 끝 공백을 제외한 내용이 같으며 실행 코드는 동일하다. 후보의 HTTP 14개·보안 헤더를 확인했고 임시 점검키를 폐기해 남은 키는 0개다. 같은 후보를 운영 주소에 승격한 뒤 HTTP 14개·보안 헤더·배포 ID·접근 보호 설정을 다시 확인했다. 다른 Vercel 프로젝트의 운영 배포는 유지됐다. 최종 점검 완료 시각은 2026-10-07 21:51(KST)다. 실제 Google 계정으로 브라우저 로그인 전 과정을 다시 수행하거나 운영 학생의 금융 거래를 실행하지는 않았다.

## 비용과 한계

- 읽기 비용을 줄이는 대신 이벤트별 파생 행과 인덱스 저장 공간을 사용한다. 저장 공간은 이력과 함께 증가한다.
- 일반 이벤트 추가는 해당 학생·과제의 새 구간을 계산한다. 과거 시점에 삽입하면 그 이후 구간, 반복 규칙을 바꾸면 해당 과제의 기록을 다시 만든다. 대량 가져오기는 SQL 문장마다 학생·과제별로 한 번씩 처리한다.
- 기록 페이지는 인덱스 기반으로 찾지만, 페이지를 보는 동안 새로 들어온 기록을 기존 스냅샷에서 제외하기 위한 필터 비용이 추가될 수 있다. 모든 상황에서 DB 스캔 행 수가 정확히 50개라는 의미는 아니다.
- 여러 학급의 합성 읽기 측정은 운영 서비스 최대 수용 인원이나 실제 인터넷 응답 시간을 증명하지 않는다. 실제 사용자 세션의 Google 로그인·금융 거래·운영 부하 시험과 구분한다.
- Google 로그인 자체의 Google 라이브러리 사용은 남는다. 이번 변경으로 Google SDK 전체가 운영 빌드에서 제거되었다고 주장하지 않는다.
- 기존 매점의 학생 번호 조회 정책, 거래 취소 시 음수 잔액 허용, 기존 Google Sheets 배포는 유지한다.

## 재현과 복구
